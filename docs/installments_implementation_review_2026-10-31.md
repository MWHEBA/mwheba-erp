# Installments implementation review — 2026-10-31

Verdict: not ready for acceptance. This review covers the current working-tree implementation, including untracked services, models, migrations, templates, and tests. No application code was changed. Diagnostic tests were added under `scratch/`.

## Validation

- The six existing installment test modules passed: 159 tests.
- Adjacent cheque and sales lifecycle tests passed: 73 tests.
- Eleven additional regression checks failed on SQLite, without mocked financial services. Reproduction source: `scratch/test_installment_review_regressions.py`. Results: `scratch/installment_review_results.xml`.
- `python manage.py check --settings=tests.settings` completed with one cache backend warning (`users.W001`).
- Migration drift check failed: Django proposes `utils/migrations/0002_alter_systemlog_id.py`. This is outside the installment changes; attribution to this feature is not established. No migration was applied or generated by the review.
- `git diff --check` reports a trailing blank line in `sale/services/pricing_validator.py:384`.
- No browser, production database, gateway, real network integration, or MySQL concurrency testing was performed. Tests use in-memory SQLite and disable migrations; their success does not validate migration execution or row locking.

## Confirmed defects

### F1 — P1: invoice creation does not invoke the installment engine

`InstallmentEngine.generate_installment_plan` has no production caller; repository search finds its definition and tests only. The invoice form and create view do not collect or submit installment configuration, and `SaleService.create_sale` does not initialize these fields or create the plan before posting the invoice. The generated-plan service updates amounts later but does not amend the original invoice journal. Thus the core create-invoice-plus-plan-plus-down-payment workflow is not implemented as an atomic posting path.

Related source: `sale/services/installment_engine.py:152`, `sale/services/sale_service.py:132`, `sale/services/sale_service.py:185`.

The supply-contract stock and COGS guards also read `sale.plan_type`, although the type belongs to `sale.installment_plan`. Consequently normal persisted supply plans do not activate the suppression condition. Sources: `sale/services/sale_service.py:192` and `:934`.

### F2 — P1: subledger omits installment interest and settlements

`PartnerSubledgerService.record_sale_invoice` still uses `sale.total` and subtracts payments and returns only. A 60,000 invoice with a 6,000 markup has a 66,000 invoice claim but a 60,000 subledger balance. Persistent settlements are not included either. Fix all writers and reconciliation readers around one claim definition.

Source: `financial/services/partner_subledger_service.py:30`. Reproduced by `test_subledger_matches_installment_claim`.

### F3 — P1: quick collection reports a posted receipt without a ledger entry

The endpoint directly creates a `SalePayment` with `status='posted'` and `financial_status='synced'`, but calls no posting gateway. `SalePayment.save` only updates payment status. A successful full collection of 22,000 created zero journal entries in the regression test. Route this through the central payment posting service, with account permissions, currency settlement, and financial evidence.

Source: `sale/installment_views.py:322`. Reproduced by `test_full_quick_collection_posts_ledger`.

### F4 — P1: partial quick collection returns HTTP 500

The partial branch accesses `InstallmentCashStatus.PARTIALLY_COLLECTED`, which does not exist. The actual enum member is `PARTIALLY_PAID`. A 1,000 collection against a 22,000 installment raises `AttributeError` and rolls back the request.

Source: `sale/installment_views.py:350`. Reproduced by `test_partial_quick_collection_returns_success`.

### F5 — P1: composite reversal deletes unrelated and historical payment state

Reversal selects every `COLLECTED` installment in the plan and sets all payment, waiver, rebate, and principal settlement counters to zero. It neither limits the changes to the selected batch nor subtracts the batch's original allocations. A prior 11,000 partial payment was erased; an unrelated fully paid 22,000 installment was reopened in a separate reproduction.

Source: `sale/services/settlement_reversal_service.py:125`. Reproduced by `test_reverse_preserves_prior_partial_payment` and `test_reverse_preserves_unrelated_paid_installment`.

Persist per-item component allocations for each batch and reverse only those deltas. Handle later transactions explicitly rather than resetting counters.

### F6 — P1: individual reversal accepts a component of a composite batch

`reverse_individual_settlement` does not reject a nonempty `batch_id`. Passing the discount component of an early-settlement batch reverses the entire shared journal while marking only that component reversed; the payment and other components remain posted. Composite routing must be enforced in the service itself.

Source: `sale/services/settlement_reversal_service.py:164`. Reproduced by `test_composite_component_cannot_be_reversed_individually`.

### F7 — P1: contra settlement reduces the invoice twice

The service creates both an invoice-affecting `InstallmentSettlement` and a posted `SalePayment` for the same amount. Both are deducted by `Sale.amount_due`. A single 22,000 offset against a 66,000 claim leaves 22,000 instead of 44,000. Use one authoritative debt-reduction representation and retain the other as nonfinancial evidence if required.

Source: `financial/services/contra_settlement_service.py:169` and `:182`. Reproduced by `test_contra_reduces_invoice_only_once`.

### F8 — P1: refund branch over-reduces other installment debt

The refund branch caps the rebate applied to the selected installment's principal, but the invoice-affecting rebate record stores all prepaid interest, including the amount separately credited as a customer refund. A selected installment with 1,000 principal and 100 interest remaining, and 1,900 prepaid interest, generates a 900 refund; the invoice then shows 43,100 while untouched installments total 44,000. Only the portion used to settle invoice debt may affect its due balance. Persist the refundable excess separately and reverse it with the batch.

Source: `sale/services/early_settlement_service.py:450`. Reproduced by `test_refund_branch_preserves_debt_of_other_installments`.

### F9 — P1: collection surplus is not durably allocated

The engine's final-installment surplus only changes `customer.balance`; the receipt stores the installment amount, not the full collected amount, and no prepaid transaction or surplus journal is created. Collecting 23,000 against a final 22,000 installment records only 22,000 of payment evidence.

The quick endpoint has a different failure: it stores the full amount but updates only the current installment, leaving later installments unchanged. In the regression, the extra 1,000 never reaches the next installment. Both paths must use the same allocation/posting engine.

Sources: `sale/services/installment_engine.py:322` and `:358`, `sale/installment_views.py:306`. Reproduced by `test_excess_collection_has_durable_payment_evidence` and `test_quick_overpayment_allocates_next_installment`.

### F10 — P1: curtailment succeeds without cancelling commercial principal

`credit_note` is optional and unused. The service waives deferred interest and changes the item state to `WAIVED`, but neither creates nor validates a posted commercial credit note, and does not settle the cancelled principal. It can report successful curtailment while the invoice still claims the cancelled goods. Delivery validation also checks only the singular delivery-note relation, not the many-to-many call-off deliveries.

Source: `sale/services/curtailment_service.py:56` and `:162`. Reproduced by `test_curtailment_requires_commercial_credit` (the operation succeeds without raising).

### F11 — P1: shared cheque swap returns the paper while retaining other allocations

The shared-cheque check only compares the new cheque's total amount. The operation then selects a single old allocation using `.first()`, reverses only it, and returns the entire old cheque to the drawer. Other installment/invoice allocations and any advance share remain on the returned cheque. A full-value replacement does not fix this: all active old allocations and advance reservations must move atomically before return.

Source: `cheques/services/swap_service.py:65`, `:90`, and `:121`. Static source confirmation; no additional swap reproduction was run.

## Additional integration and operational gaps

- `amortize_matured_installments_for_period` has no caller outside its definition. `PeriodControlService.close_period` does not invoke the new interest amortization service. Direct service tests do not prove automated period-close integration.
- `DeliveryBlockService` has no caller outside its own module and tests, so its guards do not enforce the real delivery-posting path.
- `InstallmentOperationAudit` is declared and tested as a model but is not used by the production services. Required request fingerprints and durable replay behavior are absent. Services also acquire locks in incompatible orders (item first, sale first, plan first, or cheque first); no claim of MySQL concurrency safety can be made.
- Radar queries use nonexistent cheque status strings `IN_SAFE` and `BANK_DEPOSITED`, producing zero cheque KPIs for valid `IN_PORTFOLIO` / `UNDER_COLLECTION` records. The low-risk filter references nonexistent `PaperCoverage.FULLY_COVERED` and will raise an exception.
- Customer balance recalculation in `sale/signals.py` does not subtract the new persistent settlements. The new quick/early payment constructors also omit several existing currency settlement fields. Further cross-currency and balance-snapshot integration work is required.
- The acceptance matrix contains examples that only create models or assert arithmetic constants, including the mobile workflow and return markup examples. Passing these tests does not establish that the corresponding production workflows exist.

## Acceptance criteria for the next review

Fix the ownership of debt reduction and posting first, preserve exact per-operation component allocations for reversal, and wire the services into the real invoice/delivery/period-close entry points. Then turn the eleven diagnostic checks into maintained regression tests, add shared-cheque replacement and multi-currency coverage, and validate migrations and lock behavior on the supported production database engine.
